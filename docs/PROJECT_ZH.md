# LoopLocal：社区维修与工具共享平台

## 项目定位

**建议 FYP 标题：** LoopLocal: An Explainable Community Repair and Tool-Sharing Platform for Circular Neighbourhoods。

**中文题目：** 面向循环社区的可解释维修匹配与共享工具管理系统。

对应联合国 **SDG 12：负责任消费和生产**，重点支持 **Target 12.5** 的废弃物预防、减量和再利用。维修让物品继续使用；共享工具让居民在短期需要时借用工具；活动帮助居民学习维修技能。

这是可以运行、有持久数据库、有真实业务规则的 Web 系统。前端英文，适合软件工程答辩；后端 Python Flask + SQLite，部署不需要付费 API 或云端数据库。界面、业务代码与文档为本项目编写，没有复制所参考项目的源码。不能保证世界上不存在类似系统；创新在于适合本地社区的流程整合与可解释性。

## 问题陈述

居民遇到小家电、家具或衣物损坏时，常遇到四个问题：不知道附近谁能帮忙、不知道自己能否安全处理、为了偶尔使用而购买工具、缺少维修过程与结果记录。单纯的维修目录或二手市场不能覆盖完整的维修协作过程。

LoopLocal 将「发现问题、连接技能、借用工具、参与学习、记录维修、查看社区成效」放在同一套系统中。目标用户为马来西亚城市社区居民、维修志愿者及社区中心管理员。

## 主要创新点

1. **可解释的维修匹配**：技能 60 分、同区 25 分、工作量最多 15 分。展示每一项推荐理由；不是假装运行机器学习。志愿者必须具备相应的自报技能，最多同时处理三张维修单。
2. **隐私友好的物品维修护照**：完成维修后产生不可轻易猜测的公开 URL，展示类别、重量和状态时间线。个人姓名、地点、讨论及私人维修笔记不会公开。可以打印为 PDF，或复制链接随物品转交。
3. **真实的共享工具库存逻辑**：按每天计算多份工具库存，防止重叠预约；借出和归还由管理员确认；逾期未还会阻止继续承诺库存；并发操作通过事务保护。
4. **从维修到学习的闭环**：居民可以报名维修活动；活动容量、取消、退出和通知由系统控制。
5. **透明环保成效**：只统计完成的维修，单件只计一次。重量来自用户估算，CO₂e 是明确标示的假设情景，不把演示系数包装成真实减排数据。

## 三种角色

| 角色 | 可进行的操作 |
|---|---|
| 居民 | 注册、提交和查找自己的维修、讨论、取消、借工具、报名活动、查看护照和成效 |
| 维修志愿者 | 居民功能、技能资料、查看待处理维修、接单、更新处理状态、提交维修记录 |
| 管理员 | 全部维修审核、会员启停、工具新增与下架、借出归还、创建取消活动、审计日志、成效 CSV |

账号权限由服务器验证，不能通过修改浏览器表单注册成管理员。

## 功能演示建议（约 10–12 分钟）

1. 以居民 `resident@looplocal.test` 登录，介绍首页、统计、维修列表与活动。
2. 新建 Electronics 类别的台灯维修，描述不少于 20 字符，填写重量与安全检查。
3. 展示系统推荐的志愿者及评分理由。说明自报技能不等于专业认证。
4. 退出，以 `fixer@looplocal.test` 登录，切换 Community bench，打开刚才的维修并接单。
5. 发送一条私人消息，将状态改为 In progress；记录实际操作及检查后改为 Repaired。
6. 打开 Item passport。说明公众看不到用户姓名、地点和私人消息；演示打印和复制链接。
7. 在工具库预约 Cordless drill。尝试另一账号预约相同日期，展示库存不足提示。
8. 以 `admin@looplocal.test` 登录，在工具库完成 Check out 和 Record return。
9. 新建一个小容量活动，让居民报名；展示人数变化和取消活动通知。
10. 查看 Our impact、类别统计、CSV，以及后台审计记录。
11. 展示测试，包括容量和抢单的并发测试；说明哪些功能不在当前范围。

所有示范账号初始密码均为 `LoopLocal2026!`，仅用于本机演示。不要把带公开测试密码的数据库部署为公共服务。

## 建议论文结构

- Chapter 1：背景、问题陈述、目标、范围、SDG 对应。
- Chapter 2：循环经济、社区维修、工具共享及现有系统比较。参考 [RESEARCH.md](RESEARCH.md)，进一步加入学校要求的同行评审文献。
- Chapter 3：需求分析、开发方法、架构与数据库设计、安全和伦理。
- Chapter 4：按真实模块讲解实现、状态机、匹配公式及并发控制。
- Chapter 5：自动化测试、浏览器验证及真实用户验收研究。
- Chapter 6：结论、限制与未来发展。

仓库文档是项目技术材料与提案基础，不是已经完成的学术论文。请按学校规定引用资料、说明工具辅助情况，并用自己开展的研究支持最终论证。

## 可以开展的实际评估

以下是建议研究计划，**尚未执行，不应当作研究结果**：

- 招募居民、维修志愿者与管理员，完成五个主要任务，记录成功率、耗时与错误。
- 对比按名字随机排列和可解释评分排列时的志愿者选择体验。
- 让真实维修人员评审安全提示、技能要求及工作流程。
- 测量修复后仍正常使用的比例，验证「已维修」是否真的延长使用寿命。
- 使用 SUS 或学校认可的问卷；保留知情同意与匿名化记录。

## 明确范围

系统没有付款、收费押金、邮件/SMS、地图导航、AI 图像判断、专业维修认证或真实碳排测量。当前通知为站内通知，匹配为规则评分。采用单社区中心、单实例 SQLite 的范围；更大规模需要 PostgreSQL、多中心库存、可靠任务队列与进一步运维支持。
